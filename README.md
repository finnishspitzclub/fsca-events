# akcal

Pulls AKC event data for Finnish Spitz nationwide, stores it, and drives the
Finnish Spitz Club of America events page — a Google Calendar (colored by
timezone) plus a monthly US event map. Also still emits an `.ics`.

Started as a personal Colorado/Wyoming tracker for one dog; now the national
breed-club feed. Runs on a cron; the breed/scope knobs are at the top of
`akcal.py`.

## Status

`akcal.py` is written and verified end to end. The downstream half is tested
against synthetic fixtures — store, change detection, and ICS rendering all
validate (CRLF, 75-octet folding, escaped separators, unique UIDs, exclusive
DTEND). The **network half is now verified too**: the request schema and
`map_record()` were derived from a devtools capture (see `SCHEMA.md`) and
confirmed against live data — all seven reference events in SCHEMA.md §7
reproduce exactly (dates, closing dates, status, per-breed counts).

The search is now **breed-scoped** (Finnish Spitz, `breedCode "313 "`) rather
than all-breed. That is deliberate: `completedLastYear` only comes back when the
request names the breed. Config lives at the top of `akcal.py`
(`BREED_*`, `FETCH_STATES`).

If the endpoint ever changes shape, re-derive it from devtools: open
`https://webapps.akc.org/event-search/`, run a search, copy the request body
from the network tab — that is ground truth. (`probe` still exists for a quick
"does it still answer?" check.)

**Heads up on the existing `events.db`:** its 123 rows are stale — nationwide
all-breed data from the old guessed payload, not the breed-scoped CO/WY design.
`db()` migrates the schema non-destructively, but the old rows are junk. Delete
`events.db` and re-`fetch` for a clean store.

## The question that decides the architecture

During the probe, check whether AKC's response carries **judge panels** and
**entry closing dates**, or only the event skeleton (event number, club, dates,
location, competition type).

- Carries both → single source, done, nothing else to build.
- Skeleton only → closing dates and judges must come from superintendents, and
  that changes v2 substantially.

Worth answering before building anything on top of this.

## What's known

**Endpoint:** `POST https://webapps.akc.org/event-search/api/search/events`
No auth, no proxy required as of ~June 2026. Caps at 1,000 events per request,
hence the 14-day windowing in `fetch`.

**Per-event AKC detail page** (this is where per-breed "Competed Last Year"
counts live, which the search endpoint probably does not return):
```
https://www.apps.akc.org/apps/events/search/index_results.cfm?action=plan&event_number={event_no}
```

**Closing date rule, verified empirically** across ~25 events: entries close on a
**Wednesday at noon, 16–17 days before day one**, in the *superintendent's*
office timezone — Onofrio uses the show's local Mountain time, Foy Trent uses
Central (Sturgeon MO), BaRay uses Pacific (Burlington WA). Useful as a sanity
check on whatever the API returns.

**Entry opening offset is NOT verified.** One observed case (37 days) but the
Wednesday pattern is a closing-date signature, so treat opening as unknown.

**Superintendent distribution** in a 100-event Non-Sporting sample: Onofrio 40,
MB-F 24, BaRay 16, Jim Rau 7, Foy Trent 7, Jack Bradshaw 6.

## National feed → website (calendar + map, color-coded by timezone)

This drives the Finnish Spitz Club of America events page. `fetch` pulls
**all 50 states + DC** (one call per state per year window; ~2 min at 2s pacing).
Two automated outputs, both regenerated by `sync`:

- **Google Calendar** (`gcal`) — writes every Finnish-Spitz-eligible show into
  the calendar embedded at finnishspitz.org/events, one event per show + one
  "entries close" reminder, colored by timezone.
- **Map** (`map`) — a self-contained `events-map.html`: the current month's
  shows pinned on a US map, colored by timezone, click for details. Data is
  baked in at generation time, so it never needs manual updates.

The `.ics` path can't color-code (Google renders a *subscribed* feed in one flat
color and ignores per-event color hints), which is why the calendar is written
through the **Calendar API** rather than published as a feed. This also gets
near-instant updates and real add/update/delete sync.

Colors are by **US timezone** — ~6 buckets covering all 50 states, which reads
better nationally than any regional clustering. Edit `STATE_TZ` / `TZ_COLOR`
(calendar) / `TZ_HEX` (map) at the top of `akcal.py`.

| Timezone | Calendar color | Map pin |
|---|---|---|
| Eastern | Blueberry | blue |
| Central | Basil | green |
| Mountain (+ AZ) | Tangerine | orange |
| Pacific | Tomato | red |
| Alaska | Grape | purple |
| Hawaii | Lavender | lavender |

### One-time setup (service account — fully headless, no expiring tokens)

1. **Create a project + service account.** In the [Google Cloud Console](https://console.cloud.google.com):
   create (or pick) a project → **APIs & Services → Enable APIs → Google Calendar API → Enable**.
   Then **IAM & Admin → Service Accounts → Create service account** (any name).
   Open it → **Keys → Add key → Create new key → JSON**. Save the downloaded
   file as `service-account.json` next to `akcal.py` (or point `AKCAL_GCAL_KEY`
   at it). It contains a private key — treat it like a password, don't commit it.
2. **Share your calendar with the service account.** Copy the service account's
   email (`...@...iam.gserviceaccount.com`). In Google Calendar → your calendar →
   **Settings and sharing → Share with specific people → Add** that email with
   **"Make changes to events."** This is what lets the headless account write.
3. **Get the calendar ID.** Same settings page → **Integrate calendar → Calendar
   ID** (e.g. `...@group.calendar.google.com`). Set it as `AKCAL_GCAL_CALENDAR_ID`.
4. `pip install -r requirements.txt` (adds `google-auth`).

### Run it

```
python3 akcal.py sync --dry-run     # fetch + show the push plan, no writes, no auth
python3 akcal.py sync               # fetch, push to calendar, regenerate the map
python3 akcal.py map                # (re)build events-map.html from the store only
```

`sync` = `fetch` a rolling window (today−7 .. today+540 days, so cron never needs
date edits) → `gcal` → `map`. The calendar push is idempotent: deterministic
event ids mean re-runs update in place, and events that drop out of the store
are deleted from the calendar (`--no-prune` to disable). `map` alone rebuilds
the HTML from whatever is stored (`--month YYYY-MM`, `--months N`, `--out PATH`).

### Schedule it

**Ubuntu box (recommended — always on).** Edit `sync.sh` (calendar id + key path),
then `crontab -e`:

```
0 6,18 * * *  /path/to/akcal/sync.sh >> /path/to/akcal/sync.log 2>&1
```

**Windows Task Scheduler** (if the box isn't ready): set the two env vars, then

```powershell
$env:AKCAL_GCAL_CALENDAR_ID="...@group.calendar.google.com"
$env:AKCAL_GCAL_KEY="C:\Users\dhole\Desktop\akc_call_tool\service-account.json"
schtasks /create /tn akcal-sync /sc daily /st 06:00 /tr "python C:\Users\dhole\Desktop\akc_call_tool\akcal.py sync"
```

Twice a day is plenty — Google is the live view; this just keeps it current.

### Publishing the map

`sync` regenerates `events-map.html` locally. Getting it onto finnishspitz.org
depends on how that site is hosted — **TBD**:

- **WordPress / CMS** — upload `events-map.html` and embed it in an `<iframe>`,
  or paste its body into a Custom HTML block. The cron then needs to push the
  file up (SFTP/API) — a few lines added to `sync.sh` once we know the host.
- **Static site (Netlify/Cloudflare Pages/S3)** — `sync.sh` commits/uploads the
  file on each run; the page updates on deploy. Matches the original "nothing
  inbound at home" goal.
- **Manual for now** — `sync` produces the file; upload it yourself until the
  push is wired. Nothing breaks; it's just not yet hands-off.

## Design notes

- `map_record()` keeps the **raw JSON blob** alongside normalized fields. A bad
  mapping is fixable from the store; no re-fetch needed.
- Every closing date emits its **own VEVENT with a 3-day VALARM**. That is the
  point of the tool — show dates are memorable, a Wednesday-noon deadline
  sixteen days out is not.
- UIDs are stable (`akc-{event_no}@akcal`), so republishing updates events
  rather than duplicating them.
- Google Calendar refreshes subscribed ICS URLs slowly and unreliably — often
  12–24h regardless of `REFRESH-INTERVAL`. Do not publish a change the day
  before a closing and expect it to land.
- Pacing is deliberately conservative (2s between calls). This pulls a calendar
  a few times a week. Keep it that way.
